# Agent Tracking Stack

Local stack for tracking cost/efficiency of AI coding agents (Claude Code and Codex CLI) with full call-chain tracing.
Every LLM call is routed through a local LiteLLM proxy; its `generic_api` callback POSTs the full `StandardLoggingPayload` to `webhook`, which enqueues it onto `redis` completely unmodified (no parsing on webhook's own request path - it's I/O only); `webhook-worker` drains that queue in batches, computes a compact event per payload (see `build_event` below - the messages-dependent parsing happens here, never on webhook's own request path, and never a ClickHouse write from webhook itself), and does the actual ClickHouse inserts. Grafana reads from ClickHouse; a CLI session reads back out via the `mcp-server` MCP server.
This split exists because ClickHouse handles a few large batched inserts far better than many small per-request ones - see "Architecture > Queue in front of ClickHouse" below.

## Stack at a glance

- `litellm` - proxy every Claude Code/Codex CLI call routes through; its `generic_api` callback feeds `webhook`.
- `webhook` (2 replicas, `webhook-1`/`webhook-2`) - accepts LiteLLM's callback POSTs, enqueues onto `redis`; zero ClickHouse access, zero JSON parsing on its request path.
- `webhook-worker` - drains `redis`, builds compact events, does the actual batched ClickHouse inserts (see Architecture below).
- `redis` - Streams buffer between `webhook` and `webhook-worker`.
- `clickhouse` - stores `agent_events`/`agent_usage`/`agent_messages`/`agent_invocations`/`ingest_raw`/etc.
- `grafana` - dashboards reading from ClickHouse (`agents_overview.json`).
- `mcp-server` - the only sanctioned ClickHouse read path for agents/CLI sessions (`query`/`profile_query`/`whatsup`).
- `load-balancer` - nginx gateway in front of every other service's host port (see Architecture > Gateway below).
- `backup` (tools-profile service) - backup/restore for `clickhouse`/`litellm-db`/`grafana-data` (see the `infra-backups` skill).
- `langfuse-*` (opt-in `langfuse` profile) / observability stack (opt-in `observability` profile) - optional, see README.

## Scratch pads and project memory

`.claude/data/` is a git-ignored local-data root, one subdirectory per purpose - not a general dumping-ground temp directory:
- `.claude/data/goals/` - scratch state carried between iterations of a single `/goal` loop (e.g. notes on what's already been checked or changed this loop). Not for anything meant to survive past that loop/session.
- `.claude/data/query_perf_runs/` - saved `services/grafana/scripts/query_perf.py` benchmark runs (see `.claude/agents/sql-expert.md`/`query-perf-runner.md`). Unlike `goals/`, these are meant to persist and be `diff`ed against later, potentially across sessions - don't treat this subdirectory as scratch or clear it casually.

Cross-session memory of you-the-agent is a separate system entirely (`~/.claude/projects/*/memory/`, outside this repo) - see the comment policy's note on that below.

**When the user tells you, as an ongoing/standing rule, that you're not allowed to do something (or must always do something) in this project - not a one-off correction - save it to that cross-session memory *and* propose folding it into this file (`AGENTS.md`) or `README.md` as appropriate.** Memory is agent-only and invisible to the user and to other agents/sessions reading this repo; a standing rule that matters to how the project is worked on belongs here (or in `README.md` if it's user-facing) so it's visible to everyone, not just recoverable by you across sessions.

## Architecture

### Why a queue in front of ClickHouse

- ClickHouse handles a few large batched inserts far better than many small per-request ones (merge/part amplification, connection overhead per insert). The old design had `webhook`'s request handler doing up to 4 separate `client.insert()` calls per `StandardLoggingPayload`, synchronously, inside the HTTP handler - fine at low volume, but with many developers routing concurrent Claude Code/Codex sessions through LiteLLM, that's many small inserts per second hitting ClickHouse directly, with backpressure onto `webhook` (and from there, retries from LiteLLM) if it falls behind.
- `webhook` now only ever enqueues onto `redis`. `webhook-worker` is the only thing that talks to ClickHouse for `/api/v1/metrics` traffic - it's also the only thing that calls `clickhouse_ingest.build_event()` (per payload, on decode - pure, no I/O), in batches via `clickhouse_ingest.ingest_events_batch()`. Keeping `build_event()`'s CPU-bound parsing (regex classification, message scanning, JSON work) off `webhook`'s own request path was itself a fix, not just batching - load testing (`make loadtest`) showed p99 request latency climbing under sustained concurrency when `build_event()` ran inline in `webhook`'s single-threaded event loop, serializing behind whichever request's parsing got there first.
- Removing `build_event()` alone wasn't enough: `webhook-1`/`webhook-2` (each `cpus: 1.0`) still pegged at 65-96% CPU under the same load, even with `build_event()` gone. The culprit was `request.json()`/`json.dumps()` themselves - parsing and re-serializing a ~360KB-1.5MB `StandardLoggingPayload` twice per request (parse in, re-serialize out) is real CPU work. `queue_client.enqueue_raw(body: bytes)` is the fix: `server.py`'s handler reads `await request.body()` (raw bytes, not `.json()`) and, for the common single-payload case, `XADD`s those bytes onto `redis` completely unparsed - zero `json.loads`/`json.dumps` on webhook's request path. Only a bundled `log_format: json_array` body needs an actual parse to split it into one Redis entry per payload, falling back to `enqueue(payloads: list)` for that case (same function the `CAPTURE_ENABLED` path already uses, since capture-file naming needs each payload's `session_id` anyway).
- `XREADGROUP ... BLOCK` unblocks as soon as it sees a single entry, not once `COUNT` is filled, so a naive `XREADGROUP COUNT 500 BLOCK 2000` loop would insert almost every event as its own batch of one under normal (non-bursty) traffic - the actual cause of ClickHouse taking constant tiny inserts instead of real batches. See "Workers" below for the fix.

### Workers (`webhook-worker`)

- `worker.py` fixes the tiny-batch problem above by accumulating `build_event()`-decoded events across repeated `XREADGROUP`/`XAUTOCLAIM` calls into a buffer, only flushing (one `client.insert()` per table for the whole batch) once `config.BATCH_SIZE` is reached or `config.FLUSH_INTERVAL_MS` has elapsed since the window opened, whichever comes first.
- `agent_name`/`agent_version` can't be resolved at `build_event()` time (needs a `SELECT` against `agent_invocations`, which only makes sense once that batch's own invocation rows are committed) - left blank there and patched in by `ingest_events_batch()`, batch-side, with a per-batch cache so repeated `agent_invocation_id`s only trigger one `SELECT` each.
- See "Rules to not violate" below for the `source_row`/`ingest_raw` full-payload-preservation rule and its memory-footprint sizing.

### Gateway (`load-balancer`)

- A single nginx service (`services/load-balancer/`) sits in front of every service that used to publish its own host port directly: `webhook` (via `webhook-1`/`webhook-2`), `litellm`, `grafana`, `mcp-server`, `clickhouse` (both its HTTP interface and native protocol), and `langfuse-web` (opt-in `langfuse` profile). Each keeps its original `listen`/host port (`WEBHOOK_PORT`/`LITELLM_PORT`/`GRAFANA_PORT`/`MCP_SERVER_PORT`/`CLICKHOUSE_HTTP_PORT`/`CLICKHOUSE_NATIVE_PORT`/`LANGFUSE_PORT`) - `http://localhost:<port>` for each is unchanged, only the container actually terminating the connection changed. `langfuse-web`'s own container-internal port (3000) collides with `grafana`'s, so nginx listens for it on its own internal `3001` instead - purely an nginx-internal socket choice, unrelated to `LANGFUSE_PORT`, which still controls the host side exactly as before.
- **Routing stays port-based, not path-prefixed or subdomain-based.** This stack has no domain or local DNS infra anywhere - every consumer (README, `Makefile`, `.mcp.json`, `make env`'s printed `ANTHROPIC_BASE_URL`/`AGENT_CLI_TRACKING_API_URL`) already addresses services as `http://localhost:<PORT>`, so per-port `server{}` blocks in `nginx.conf` reuse that with zero client-facing change. Path prefixes would need every backend to tolerate a stripped/rewritten prefix (unverified for LiteLLM's UI/API and the MCP server's `streamable-http` transport) and would ripple through every hardcoded URL above; subdomains would need `/etc/hosts`/DNS infra that doesn't exist here. Revisit only if this stack ever runs behind a real external domain.
- **Webhook load balancing is real `least_conn`, not a fixed split**, which needs static backend addresses: nginx's `least_conn` only works inside a static `upstream{}` block, and open-source nginx (no nginx-plus) resolves a `server <hostname>` entry once, at startup/reload, never again. So `webhook-1`/`webhook-2` get **static IPs** (`172.28.1.11`/`172.28.1.12`) in `docker-compose.yml`'s `networks:` block instead, letting `nginx.conf`'s `upstream webhook_backend { least_conn; ... }` address them directly - no DNS involved, so a replica recreate can't go stale. The network's `ipam.ip_range` (`172.28.0.0/24`) deliberately excludes the `172.28.1.x` range the static IPs live in, so Docker's automatic allocator can never hand one of those addresses to some other container first (hit exactly this race in testing - `litellm`/`mcp-server` grabbed `172.28.0.11`/`.12` before `webhook-1`/`webhook-2` could claim them, before the exclusion existed). `max_fails`/`fail_timeout` on each `server` line add nginx's built-in passive health check on top.
- **The other five backends (litellm/grafana/mcp-server/clickhouse/langfuse-web) use a `resolver 127.0.0.11 valid=10s;` + `set $var host:port; proxy_pass http://$var;` pattern instead** - no static IP needed since there's nothing to `least_conn` between (one backend each), but a literal `proxy_pass http://host:port;` still gets resolved once at parse time even with `resolver` set, so the variable indirection is what actually defers resolution to request time. Without it, a routine `docker compose up -d --build <service>` recreate would 502 forever until nginx itself restarted. ClickHouse's native protocol (port 9000, raw TCP) uses the same variable trick inside a `stream{}` block instead of `http{}`. `langfuse-web` not existing at all (profile not enabled) behaves the same way as any other backend not being up yet - per-request 502s, no crash.
- **`load-balancer` has no `depends_on` on anything, deliberately.** nginx tolerates any backend being down (502s a request until it's reachable, self-heals via the resolver/passive-check mechanisms above), and none of the six backends it fronts should be forced to start (or be unstartable on their own) just because the gateway is also running.

### Dev/prod split

- `docker-compose.yml` is prod-default: no service in it has `command:`/`entrypoint:`, or a bind mount for source/config (only named data volumes and genuine host-system mounts like `docker.sock`, `/proc`/`/sys`). `services/litellm/user_configs/*.yaml` (gitignored, may carry real remote-model hosts/keys) is baked into the `litellm` image at build time in prod too - not bind-mounted, so a new/changed source needs `docker compose build litellm` in prod.
- Everything needing a live-editing workflow (bind-mounted `services/*/src`, `config.yml`, Grafana's dashboards/provisioning, `litellm`'s `user_configs/` only, `--reload` for `webhook`/`mcp-server`) instead lives in `docker-compose.dev.yml`, an override file layered on top.
- `Makefile`'s `ENVIRONMENT` (`.env`, default `development`) picks which files `check-env` puts in `COMPOSE_FILES`: anything but exactly `production` layers both files; `production` uses `docker-compose.yml` alone. Every target depends on `check-env`, which prints `⚠️  ENVIRONMENT=...` before anything else runs. `ENVIRONMENT` is captured from the shell/`.env` *before* `include .env` runs and restored after, specifically so a shell-exported `ENVIRONMENT=production make start` isn't silently overwritten by `.env`'s own `ENVIRONMENT=development` default (`include`'s plain `=` assignment is file-origin, which GNU Make lets override an environment-origin variable - the reverse of what you'd expect).
- Static per-image config (Grafana provisioning, LiteLLM's `config.yaml`, `redis.conf`, etc.) is still baked into each service's own image via `COPY` in its Dockerfile, in both dev and prod, unchanged. What moved is *runtime role selection* for the one image that serves four different compose services (`webhook`/`webhook-worker`/`webhook-reparse`/`clickhouse-migrate`, all built from `services/webhook/Dockerfile`): instead of a compose-level `command:` picking the entry point, `services/webhook/docker-entrypoint.sh` (baked, `ENTRYPOINT`) dispatches on the `APP_ROLE` env var (`server`/`worker`/`reparse`/`migrate`, default `server`) set per-service in `docker-compose.yml`'s `environment:`. It also has an `if [ "$#" -gt 0 ]; then exec "$@"; fi` passthrough, so `docker-compose.dev.yml`'s `command:` override (adding `--reload` for `webhook`) still works without touching the script. `litellm` and `redis` get **no** dev override at all - both environments always run the same baked image.

## Running the load test (`make loadtest`)

Whenever the user asks for a load test, delegate the whole workflow to the `loadtest-runner` agent (`.claude/agents/loadtest-runner.md`, runs on Sonnet) rather than driving `make loadtest` inline - it owns the ask-first questions below, launching, parallel monitoring, ClickHouse verification, and the final bottleneck report end to end.

Before starting a `make loadtest` run, **ask the user** (don't assume) about three things:

- **Whether to truncate the ClickHouse ingest/agent tables first** (`agent_events`, `agent_invocations`, `agent_messages`, `agent_usage`, `ai_gateway_groups`, `ai_gateway_users`, `ingest_dlq`, `ingest_raw`, `plan_proposals`, `session_git_branch` - never `schema_migrations`). A clean baseline makes before/after row counts meaningful, but isn't always wanted.
- **Whether to restart the whole stack first** (`docker compose down` + back up, or equivalent) so every service starts from a known-good, non-degraded state before the run, rather than reusing whatever state containers happen to be in.
- **Whether to shut down `litellm`/`litellm-db` first, if they're currently up** - they share the same Docker host/resources as everything the load test measures, and load tests don't use them anyway (`loadtest.py` hits `webhook`/`load-balancer` directly, bypassing LiteLLM), so leaving them running is a free variable in the resource measurements unless the user wants them left alone for something else.

After the run, **ask before leaving `litellm`/`litellm-db` up** if they were shut down for the test (bring them back?) or if they were only started to verify something unrelated (e.g. a backup) beforehand - don't just assume either way.

If the stack gets stopped/restarted (accidentally or otherwise) while a load test or its monitoring loop is still running, treat the in-flight run as contaminated - stop the loadtest container and any monitoring process, don't try to salvage partial data, and re-run from a clean start once the stack is confirmed healthy again.

## Comment policy

- **Comment code/config economically.** Code is read rarely and comments rot faster than the code they describe. A comment should cover a non-obvious *why* (a hidden constraint, a workaround, an invariant that would surprise a reader) - not restate what the code already says. Don't try to fully document behavior in a comment; that's what clear naming/structure and tests are for. If you're about to write more than a short paragraph inline, that's a sign the content belongs in `AGENTS.md` (for future agents) or `README.md` (for users) instead, with just a pointer left in the comment.
- **Comments describe the general/hypothetical case, never this specific machine's state.** Write "this breaks under Docker Desktop's containerd image store" or "this breaks under Colima when the containerd-snapshotter driver is enabled," not "this is broken on this machine" or "confirmed broken in this dev environment." A fact about one person's current setup belongs in that person's own notes, not in a comment every future reader (on a different machine, in production) will trip over. The one exception is memory (`~/.claude/projects/*/memory/`, outside this repo) - that's explicitly the right place for machine-specific/session-specific state.
- **The main architectural picture lives in `AGENTS.md` (for agents) and `README.md` (for users) - not scattered across inline comments.** After any change that alters architecture (a new service, a changed data flow, a new required env var, a new failure mode worth knowing about), check whether `.env.example`, `README.md`, and `AGENTS.md` need updating, and update them. This step is easy to skip and easy to forget - treat it as part of the change, not a follow-up.

## Rules to not violate

- **Before running any ad hoc Bash/Read/Grep investigation, transformation, or verification inline, check whether an existing `.claude/agents/*.md` already owns that class of work.** This repo delegates aggressively (test running, load testing, ClickHouse reads, dashboard reads, script/file ops) - reinventing inline what a subagent already owns is presumptively wrong, not just wasteful. Concrete instance: a plain `ls`/`find` was kept inline as "the caller already knows what to look for," even though `script-ops`'s own scope already covers open-ended investigation before a target is even identified, not just point lookups.
- **When given multiple distinct asks in one message/session, build a `TodoWrite` task list immediately - one item per ask - and keep it current (mark the active one `in_progress`) as work proceeds.** Lets the user see what's being worked on right now instead of inferring it from a wall of assistant text. Applies to the main/orchestrating conversation - most subagents don't carry the tool.
- **Run the test suite after every change under `services/webhook/` (source or tests) - always via the `webhook-test-runner` agent, never `make test`/`pytest` inline.** Delegating keeps raw pytest output (35+ lines and growing) out of the main conversation, per this repo's usual pattern of pushing DB reads/tool output into subagents (see `clickhouse-analyst`). Do this proactively, without being asked - don't wait for the user to request a test run.
- **Skills, agents, and any config/naming this repo owns must stay CLI-agnostic.** This stack tracks Claude Code and Codex CLI equally - don't write a skill/agent body that only makes sense for one of them without saying so explicitly, and don't name a variable/file after "Claude" when the thing it controls is actually shared (a now-retired hook-era variable, `CLAUDE_TRACKING_API_URL`, once did exactly this - see git history if precedent is needed). The one exception: names Claude Code or Codex itself defines (`CLAUDE_PROJECT_DIR`, `.claude/`, `.codex/`) - don't rename those, they aren't ours to rename.
- **No per-service env defaults in Python/entrypoint code.** `docker-compose.yml` is the only place `CLICKHOUSE_*`/`REDIS_*` defaults live; `services/webhook/src/config.py` reads them with plain `os.environ[...]` (no fallback), and `services/grafana/docker-entrypoint.sh` asserts (`:?`) rather than re-defaulting. A second copy of the defaults has drifted before (the old ingest-api once silently defaulted the password to `""`).
- **Every tunable constant in `webhook`/`webhook-worker` lives in `services/webhook/src/config.py`, not scattered across modules.** `clickhouse_ingest.py`, `queue_client.py`, `worker.py`, and `server.py` all import from `.config` rather than reading `os.environ` or hardcoding their own constants - a new tunable (queue mechanics, connection settings, feature flags like `CAPTURE_ENABLED`) belongs there too, even if only one module currently uses it.
- **Never derive cost from a local price table again.** `agent_usage.cost`/`input_cost`/`output_cost` come straight from LiteLLM's own `response_cost`/`cost_breakdown` - a manually-maintained `model_pricing` table with an `ASOF JOIN` derivation used to exist for this and was removed after it was found to overcount cost by several times whenever prompt caching was in play (it priced every input token at full rate, ignoring the cache-read/cache-write discount LiteLLM already applies correctly).
- **`schema.sql` changes need a manual re-apply** on an already-initialized volume: `docker exec -i agent-tracking-clickhouse clickhouse-client --multiquery < clickhouse/schema.sql`, or drop the `clickhouse-data` volume (destroys data).
- **No ClickHouse table ever gets a TTL-based auto-delete clause - data deletion is a deliberate manual action, never something ClickHouse runs on a background schedule.** A table that could grow large instead gets `PARTITION BY` on its time column, using the half-year convention already established on `agent_events`/`agent_usage`/`agent_messages`/`ingest_raw`: `concat(toString(toYear(<col>)), '-H', toString(intDiv(toMonth(<col>) - 1, 6) + 1))`. That makes a whole half-year the natural unit for a human to `ALTER TABLE ... DETACH PARTITION` later, if archival is ever actually needed - no TTL clause does that automatically. `ingest_dlq` used to have a 30-day TTL and was migrated off it onto this same convention (`services/clickhouse/migrations/011_ingest_dlq_partition_by.sql`) for exactly this reason.
- **`harness-expert` owns every Subagent/Skill/Command's frontmatter, body style, and `<version>` marker, plus `AGENTS.md` itself - always invoke it for those edits, never hand-roll them.** Pass it the user's request verbatim as its prompt - never rewrite it into step-by-step instructions first; harness-expert works out what's needed on its own. See that agent's own file for the full convention (marker placement, why it must live in `description`/body text and not a `version:` frontmatter key, bump rules, new-entity trigger question).
- **Every subagent dispatch (`Task`/`Agent` tool), for every subagent, always translates the prompt to English first if the user's original wording wasn't already English (Russian, etc.).** Pure 1:1-meaning translation only - no instructions/steps/interpretation added on top, that's still rewriting, not translating. Cyrillic (and other non-Latin script) tokenizes ~1.5-3x worse than Latin script under Claude's tokenizer, and that cost is paid twice: once in the orchestrator's own tool-call output (the prompt itself), again in the invoked agent's input.
- **When delegating via `Task`/`Agent`, the call itself (`prompt`, and the short `description` field) carries the actual content - any extra text in that same turn, alongside the call, must stay ultra-short and only cover what genuinely had no room in the call's own fields.** Never a prose recap of the task/plan/reasoning next to the call - that duplicates what the call already says and burns tokens for no routing benefit.
- **No query ever reaches ClickHouse via `docker exec .../clickhouse-client` (or any other direct connection) - this is a base rule with no per-agent exception and no silent fallback.** All ClickHouse reads, from any agent or the main conversation, go through `mcp-server`'s `mcp__clickhouse__query`/`profile_query`/`whatsup`. If that tool rejects or fails to validate a query for any reason (an overly strict validator, a table missing from its allowlist, a query too large/complex for it) - stop and ask the user for explicit permission before running anything against ClickHouse a different way. Ask every single time this comes up, not just the first time in a session - a prior yes doesn't carry forward. This binds `clickhouse-analyst`, `sql-expert`, `dashboard-panels-builder`, `dynamictext-panel-builder`, and every other current or future agent identically; it is not a policy that lives on one agent's page. The one standing exception is internal to `clickhouse_ingest.py` itself: resolving `agent_invocation_id` → `subagent_type` needs a `SELECT` against `agent_invocations` before the write it's completing - that's part of the ingestion path, not a general read API, so it doesn't count against this rule.
- **`build_event()`'s `source_row` carries the full, untouched payload (`messages` included) - that's deliberate, not a leak.** It's the one field that isn't stripped down, since `ingest_raw` (see `clickhouse/schema.sql`) exists precisely to hold the full payload for later reparsing (`webhook/src/reparse.py`) - Redis is just the buffer in front of that ClickHouse write, same as it is for the compact per-table rows. `config.MAXLEN`/the `redis` service's `maxmemory` are sized around this larger (~360KB avg, ~1.5MB max) per-event footprint (see `services/webhook/config.yml`) - don't add a new field to `build_event()`'s dict without checking it against that budget.
- **`clickhouse-analyst`'s tools stay limited to `mcp__clickhouse__query`/`whatsup`.** Never add it Bash or any other direct ClickHouse access - it follows the base ClickHouse-access rule above with no Bash escape hatch at all.
- **`sql-expert` (called explicitly by name for ClickHouse DBA work - profiling a panel's query, evaluating a proposed rewrite) follows the same base ClickHouse-access rule above.** Its Bash access is for `services/grafana/scripts/parse_dashboard.py`/`query_perf.py` (and plain repo file reads) only - never for reaching ClickHouse directly. It proposes schema changes (new Dictionary/index/materialized column) with reasoning but never applies them itself, since `query`/`profile_query` both reject DDL server-side and there's no other ClickHouse write path given to it.
- **Any dashboard-query benchmarking (current cost, or a before/after around a rewrite) goes through `services/grafana/scripts/query_perf.py` + the `query-perf-runner` agent, driven by `sql-expert` - never a one-off hand-rolled macro substitution + `profile_query` loop.** `query_perf.py resolve`/`save-run`/`diff`/`report` are deterministic (no ClickHouse access); `query-perf-runner` (haiku) is the only thing that actually calls `mcp__clickhouse__profile_query`, keeping that loop's raw output out of `sql-expert`'s/the main conversation's context. Any dashboard panel SQL rewrite - explicitly requested or a side effect of other work - gets a `before` run and an `after` run, never just one.
- **`_ensure_app_user()`'s `CREATE USER OR REPLACE` in `services/webhook/src/migrate.py` silently wipes every grant made outside that function** (confirmed live: `system.*` SELECT from `_grant_ui_access_to_app_user_once` and `system.query_log` SELECT + `SYSTEM FLUSH LOGS` from `_grant_query_log_access_once` were both gone despite their versions showing "applied" in `schema_migrations`, after the app user got recreated). Known, not yet fixed - if `profile_query`'s `memory_usage_bytes` comes back null with a `memory_usage_warning`, or the ClickHouse Play UI's schema browser stops working, re-run the missing `GRANT` by hand (see those two functions) rather than assuming something else broke.
- **Any read of `services/grafana/dashboards/agents_overview.json` - listing panels, finding one by id/title, dumping a query, checking current `queryOptions`/`fieldConfig`/etc. - goes through the `dashboard-parser` agent, never inline `python3`/`jq`/`Read` in the main conversation.** This includes quick one-off checks and post-edit verification, not just the initial investigation - the file is large (v2beta1 schema) and re-reading it inline defeats the point of delegating. Writes (the actual JSON edit) still happen in the main conversation via `Edit`/`Write`/Bash-python, since `dashboard-parser` has no write tools - only the reading step is delegated.
- **`dynamictext-panel-builder` is scoped to Dynamic Text panels only (panel-76 "Trace" and its companion panel-77), not the whole dashboard.** Every other panel edit in `agents_overview.json` goes through `dashboard-panels-builder` instead (which reads the `dashboard-panels` skill before editing) - `spec.annotations`, `spec.variables`, dashboard-level settings, and tabs/layout stay plain `Edit`/`Write`/Bash-python in the main conversation, since neither panel-builder agent owns those.
- **`script-ops` never gets `git`.** Blast-radius judgment calls (`git`, and any state-changing `docker` command - `up`/`down`/`restart`/`build`) stay with the caller, not a delegate. **Read-only `docker`/`docker compose` inspection (`ps`, `logs`, `inspect`) always goes through `script-ops`, never inline `Bash` in the main conversation** - `docker logs` output especially is exactly the large, mechanical dump `script-ops` exists to keep out of the main conversation's context; for anything with potentially large output, it should redirect to a file and `grep` it rather than dumping the full output back. (The former `file-ops` agent was merged into `script-ops` - it had no distinct scope `script-ops` didn't already cover, just a subset of its tools.)
- **Never restart/recreate `clickhouse` or edit an existing Grafana dashboard (`agents_overview.json`) as a side effect of unrelated infra work.** Both are higher blast-radius than adding a new standalone service - treat them as a separate, explicitly-requested final step, done and confirmed on their own.
- **When validating a dashboard panel's SQL fix against ClickHouse, test the panel's literal `rawSql` with only `${...}` placeholders substituted - never a simplified/reconstructed rewrite.** A trimmed test query that drops a join/column that looks like template-variable plumbing can pass cleanly while the real query still fails (e.g. `AMBIGUOUS_IDENTIFIER` from a dropped join that was actually load-bearing).
- **Don't loosen `_validate_readonly_sql` in `services/mcp-server/src/server.py`.** There's no separate read-only ClickHouse user backing `query` - that function (single statement, SELECT/WITH only, no DDL/DML keywords, no system tables, no remote/file/URL table functions) is the only thing standing between it and a write/DDL statement.
- **No per-service `README.md` files under `services/*/`.** A full playbook for a service (setup, operation, restore procedures, etc.) belongs in the repo-root `README.md`, not a separate `services/<name>/README.md` - `services/backup/README.md` used to duplicate what's now README.md's "Backup & restore" section and was folded in and deleted for exactly this reason. `AGENTS.md` (this file) stays the terse, agent-facing summary with just the essentials and rules; `README.md` is the one place for the full, detailed mechanics a human (or an agent that rarely needs the details) would read. Don't reintroduce a per-service README even for a new service.
- **Never restart/recreate the `litellm` container without asking first, even for a config-only change (`services/litellm/config.yaml`, `custom_callbacks.py`, `docker-entrypoint.sh`).** It's the live proxy every CLI session on the machine routes through - a restart drops in-flight requests for whoever else is using it right now. Ask before `docker compose restart litellm` / `docker compose up -d litellm`, the same way you would before any other action that affects shared, currently-in-use infrastructure. Note the two aren't interchangeable once asked: `restart` reuses the container's existing environment snapshot and won't pick up new/changed `environment:` entries in `docker-compose.yml` - only `up -d` (recreate) does. Confirmed the hard way: `LANGFUSE_PUBLIC_KEY`/`SECRET_KEY` were added to `litellm`'s `environment:`, then `litellm` was `restart`ed instead of recreated - it ran for a while looking fine with zero Langfuse traces produced, because the running container never actually had the new vars.
- **Never run `docker compose build`/`docker compose up` directly - always `make build [SERVICE=<name>]`/`make up [SERVICE=<name>]` instead** (both accept an optional `SERVICE` to scope to one service; omit it to cover the whole stack). `Makefile` resolves each image group's tag from `VERSIONS.yml` via `scripts/resolve_image_version.py` into `.image-tags.mk`, which exports the `<SERVICE>_TAG` vars `docker-compose.yml`'s `image: ...:${..._TAG:-latest}` lines depend on - a raw `docker compose build`/`up` skips that resolution and produces stray image versions untied to `VERSIONS.yml`.

## Worktrees for feature work/refactors

**Starting a new feature or refactor task (not a small point fix) - use `EnterWorktree` first, before making any edits.** This isolates the work from whatever uncommitted state is already sitting in the main checkout (see the git rule below for why that state can't be assumed to be yours to touch). Small, targeted fixes (a bug fix, a one-line config change, a doc update) don't need this - only genuine feature/refactor-scale work.

- On completion, ask the user whether to `ExitWorktree action: keep` (leave the branch/worktree on disk for them to review/merge themselves) or `action: remove` (clean exit, work is done and already merged/abandoned) - don't decide unilaterally.
- Merging the resulting branch back, and any push, stays a manual step the user drives - this rule only covers isolating the work itself, not the merge.
- For running multiple independent feature/refactor tasks in parallel, use the `Agent` tool's `isolation: "worktree"` option instead (one call per task, in the same message) - each sub-agent gets its own isolated worktree/branch automatically.

## Git: ask before destructive actions

- **Never run `git checkout --`/`restore`/`reset --hard`/`clean` (or any other command that discards uncommitted working-tree changes) without asking first** - even to undo your own bad edit, even on a file that looks like it only contains your own changes. `git status` can't tell you whose changes are sitting there or how far back they go; a file already modified before you touched it is signal that discarding it isn't yours to decide. Recovery is normally impossible - a path never `git add`ed leaves no blob to recover from `git fsck`/reflog. If a change you made needs undoing, edit it back by hand instead of reverting the whole file to `HEAD`, which also wipes any pre-existing uncommitted work in the same file.
  - *Incident:* a v2beta1 dashboard edit came out reformatted (`json.dump` rewrote the whole file's whitespace); the fix used was `git checkout -- <file>`, which silently discarded unrelated uncommitted dashboard work sitting in the same file since before the session started - recovered only because another session happened to still have it.
- **This rule binds every delegated subagent too** - having Bash/git access doesn't make a subagent exempt. If a file's state looks wrong mid-task, stop and report the anomaly back to the caller instead of self-recovering with git; diagnose by reading/grepping the file's actual current content, never by diffing against a git baseline that's likely stale relative to real uncommitted work already sitting there.
  - *Incident:* mid-task on `agents_overview.json`, `dynamictext-panel-builder` compared the live file against stale `HEAD` instead of the actual working tree, misdiagnosed a large pre-existing uncommitted diff as its own corruption, and ran `git checkout -- <file>` to "recover" - wiping a full session's worth of uncommitted dashboard work. It only survived because an IDE's local-history autosave happened to flush a buffer back over the checkout moments later - luck, not a safety net.
- **The same failure has a variant with none of the four named commands - watch for it specifically.** `git show :path` (or any other command writing a stored ref's content over the live working-tree file) is functionally identical to `git checkout -- path`, even though it isn't literally `checkout`/`restore`/`reset`/`clean`. The underlying rule is broader than those four commands: never let any script hold a file's full content in memory across more than one edit, and never write a file's full content back unless every byte of that write was just read fresh, immediately before writing. A large multi-edit task (5 edits or 500) does read-edit-write as one atomic cycle per edit, in a loop - not read-once, edit-many-times-in-memory, write-once.
  - *Incident:* on `agents_overview.json` again, a `dashboard-panels-builder` ~80-panel bulk edit read the whole file into memory and did four separate whole-file read-then-write-back operations over the task - including `git show :path` to "restore" the file after its own bulk-script bug, and a later pass that found zero matches and wrote the unchanged-looking buffer back anyway for no reason. Each write silently clobbered whatever concurrent agents had changed on the live file (a panel merge, a title rename, and an in-progress column split all vanished this way).
