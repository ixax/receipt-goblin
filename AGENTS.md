# Agent Tracking Stack

Local stack for tracking cost/efficiency of AI coding agents (Claude Code and Codex CLI) with full call-chain tracing.
Every LLM call is routed through a local LiteLLM proxy; its `generic_api` callback POSTs the full `StandardLoggingPayload` to `webhook`, which enqueues it onto `redis` completely unmodified (no parsing on webhook's own request path - it's I/O only); `webhook-worker` drains that queue in batches, computes a compact event per payload (see `build_event` below - the messages-dependent parsing happens here, never on webhook's own request path, and never a ClickHouse write from webhook itself), and does the actual ClickHouse inserts. Grafana reads from ClickHouse; a CLI session reads back out via the `mcp-server` MCP server.
This split exists because ClickHouse handles a few large batched inserts far better than many small per-request ones - see "Why a queue in front of ClickHouse" below.

## Scratch pads and project memory

`.claude/data/` holds scratch state carried between iterations of a single `/goal` loop (e.g. notes on what's already been checked or changed this loop) - git-ignored, not a general temp directory, and not for anything meant to survive past that loop/session. Cross-session memory of you-the-agent is a separate system entirely (`~/.claude/projects/*/memory/`, outside this repo) - see the comment policy's note on that below.

**When the user tells you, as an ongoing/standing rule, that you're not allowed to do something (or must always do something) in this project - not a one-off correction - save it to that cross-session memory *and* propose folding it into this file (`AGENTS.md`) or `README.md` as appropriate.** Memory is agent-only and invisible to the user and to other agents/sessions reading this repo; a standing rule that matters to how the project is worked on belongs here (or in `README.md` if it's user-facing) so it's visible to everyone, not just recoverable by you across sessions.

## Why a queue in front of ClickHouse

ClickHouse handles a few large inserts far better than many small per-request ones (merge/part amplification, connection overhead per insert). The old design had `webhook`'s request handler doing up to 4 separate `client.insert()` calls per `StandardLoggingPayload`, synchronously, inside the HTTP handler - fine at low volume, but with many developers routing concurrent Claude Code/Codex sessions through LiteLLM, that's many small inserts per second hitting ClickHouse directly, with backpressure onto `webhook` (and from there, retries from LiteLLM) if it falls behind.

`webhook` now only ever enqueues onto `redis`. `webhook-worker` is the only thing that talks to ClickHouse for `/api/v1/metrics` traffic - it's also the only thing that calls `clickhouse_ingest.build_event()` now (per payload, on decode - pure, no I/O), and does so in batches via `clickhouse_ingest.ingest_events_batch()`. Keeping `build_event()`'s CPU-bound parsing (regex classification, message scanning, JSON work) off `webhook`'s own request path was itself a fix, not just the original batching change below - load testing (`make loadtest`) showed p99 request latency climbing under sustained concurrency when `build_event()` ran inline in `webhook`'s single-threaded event loop, serializing behind whichever request's parsing got there first.

Removing `build_event()` alone wasn't enough, though: `webhook-1`/`webhook-2` (each `cpus: 1.0`) still pegged at 65-96% CPU under the same load, with a matching p99 climb, even with `build_event()` gone. The culprit was `request.json()`/`json.dumps()` themselves - parsing and re-serializing a ~360KB-1.5MB `StandardLoggingPayload` is real CPU work, not free I/O, and it was happening twice per request (parse in, re-serialize out). `queue_client.enqueue_raw(body: bytes)` is the fix: `server.py`'s handler now reads `await request.body()` (raw bytes, not `.json()`) and, for the common case (one payload, not a `log_format: json_array` bundle), XADDs those bytes onto `redis` completely unparsed - zero `json.loads`/`json.dumps` on webhook's request path at all. Only a bundled array (body starts with `[`) needs an actual parse to split it into one Redis entry per payload, falling back to the older `enqueue(payloads: list)` for that case (same function the `CAPTURE_ENABLED` path already uses, since capture-file naming needs each payload's `session_id` anyway).

`XREADGROUP ... BLOCK` unblocks as soon as it sees a single entry, not once `COUNT` is filled, so a naive `XREADGROUP COUNT 500 BLOCK 2000` loop would insert almost every event as its own batch of one under normal (non-bursty) traffic - the actual cause of ClickHouse taking constant tiny inserts instead of real batches.
`worker.py` fixes this by accumulating `build_event()`-decoded events across repeated `XREADGROUP` calls into a buffer, only flushing (one `client.insert()` per table for the whole batch) once `config.BATCH_SIZE` is reached or `config.FLUSH_INTERVAL_MS` has elapsed since the window opened, whichever comes first.

`build_event()` computes both the compact per-table rows (`event_row`/`usage_row`/`message_row`) and a `source_row` carrying the full, untouched original payload (`messages` included) - destined for `ingest_raw` (see `clickhouse/schema.sql`), the one place the full payload is meant to be preserved for later reparsing (`webhook/src/reparse.py`). Redis is the buffer in front of that write, same as for the compact rows - it does not make the queue's memory footprint unbounded, since `config.MAXLEN` and the `redis` service's `maxmemory` are sized around the real per-event footprint this implies: measured against real payloads in `services/webhook/captures/**/*.json`, full `StandardLoggingPayload` averages 360KB (max ~1.5MB). `agent_name`/`agent_version` can't be resolved at `build_event()` time (needs a `SELECT` against `agent_invocations`, which only makes sense once that batch's own invocation rows are actually committed) - they're left blank and patched in by `ingest_events_batch()`, batch-side, with a per-batch cache so repeated `agent_invocation_id`s only trigger one `SELECT` each.

## Gateway (`load-balancer`)

A single nginx service (`services/load-balancer/`) sits in front of every service that used to publish its own host port directly: `webhook` (via `webhook-1`/`webhook-2`), `litellm`, `grafana`, `mcp-server`, `clickhouse` (both its HTTP interface and native protocol), and `langfuse-web` (opt-in `langfuse` profile). Each keeps its original `listen`/host port (`WEBHOOK_PORT`/`LITELLM_PORT`/`GRAFANA_PORT`/`MCP_SERVER_PORT`/`CLICKHOUSE_HTTP_PORT`/`CLICKHOUSE_NATIVE_PORT`/`LANGFUSE_PORT`) - `http://localhost:<port>` for each is unchanged, only the container actually terminating the connection changed. `langfuse-web`'s own container-internal port (3000) collides with `grafana`'s, so nginx listens for it on its own internal `3001` instead - that's purely an nginx-internal socket choice, unrelated to `LANGFUSE_PORT`, which still controls the host side exactly as before.

**Routing stays port-based, not path-prefixed or subdomain-based.** This stack has no domain or local DNS infra anywhere - every consumer (this README, `Makefile`, `.mcp.json`, `make env`'s printed `ANTHROPIC_BASE_URL`/`AGENT_CLI_TRACKING_API_URL`) already addresses services as `http://localhost:<PORT>`, so per-port `server{}` blocks in `nginx.conf` reuse that with zero client-facing change. Path prefixes (`/litellm/`, `/grafana/`, ...) would need every backend to tolerate a stripped/rewritten prefix (Grafana can via `GF_SERVER_ROOT_URL`/`GF_SERVER_SERVE_FROM_SUB_PATH`, not currently set; LiteLLM's UI/API and the MCP server's `streamable-http` transport are unverified for it) and would ripple through every hardcoded URL above. Subdomains would need `/etc/hosts`/DNS infra that doesn't exist here, purely to recreate what ports already do for free. Revisit if this stack ever runs behind a real external domain - not the case today.

**Webhook load balancing is real `least_conn`, not a fixed split**, which needs static backend addresses: nginx's `least_conn` only works inside a static `upstream{}` block, and open-source nginx (no nginx-plus) resolves a `server <hostname>` entry once, at startup/reload, never again - it can't combine with periodic re-resolution the way the other four single-backend blocks do (see next paragraph). So `webhook-1`/`webhook-2` get **static IPs** (`172.28.1.11`/`172.28.1.12`) in `docker-compose.yml`'s `networks:` block instead, letting `nginx.conf`'s `upstream webhook_backend { least_conn; server 172.28.1.11:8000 ...; server 172.28.1.12:8000 ...; }` address them directly - no DNS involved, so a replica recreate can't go stale. The network's `ipam.ip_range` (`172.28.0.0/24`) deliberately excludes the `172.28.1.x` range the static IPs live in, so Docker's automatic allocator can never hand one of those addresses to some other container first (hit exactly this race in testing - `litellm`/`mcp-server` grabbed `172.28.0.11`/`.12` before `webhook-1`/`webhook-2` could claim them, back when the static IPs and the auto-allocated range overlapped). `max_fails`/`fail_timeout` on each `server` line add nginx's built-in passive health check on top - a replica that starts failing gets skipped without needing an active healthcheck prober.

**The other five backends (litellm/grafana/mcp-server/clickhouse/langfuse-web) use a `resolver 127.0.0.11 valid=10s;` + `set $var host:port; proxy_pass http://$var;` pattern instead** - no static IP needed since there's nothing to `least_conn` between (one backend each), but a plain `proxy_pass http://host:port;` (literal, not a variable) still gets resolved once at parse time even with `resolver` set, so the variable indirection is what actually defers resolution to request time and makes the periodic re-resolution real. Without it, a routine `docker compose up -d --build <service>` recreate would 502 forever until nginx itself restarted. ClickHouse's native protocol (port 9000, raw TCP, not HTTP) uses the same variable trick inside a `stream{}` block instead of `http{}`, since it isn't an HTTP protocol. `langfuse-web` not existing at all (the `langfuse` profile not enabled) behaves the same way as any other backend not being up yet - per-request 502s, no crash.

**`load-balancer` has no `depends_on` on anything, deliberately.** nginx tolerates any backend being down (502s a request until it's reachable, self-heals via the resolver/passive-check mechanisms above), and none of the six backends it fronts should be forced to start (or be unstartable on their own) just because the gateway is also running - each should stay independently startable/skippable, same as before this gateway existed.

## Dev/prod split

`docker-compose.yml` is prod-default: no service in it has `command:`/`entrypoint:`, or a bind mount for source/config (only named data volumes and genuine host-system mounts like `docker.sock`, `/proc`/`/sys`). `services/litellm/user_configs/*.yaml` (gitignored, may carry real remote-model hosts/keys) is baked into the `litellm` image at build time in prod too - see `services/litellm/Dockerfile` - not bind-mounted; a new/changed source needs `docker compose build litellm` in prod. Everything that needs a live-editing workflow (bind-mounted `services/*/src`, `config.yml`, Grafana's dashboards/provisioning, `litellm`'s `user_configs/` only, `--reload` for `webhook`/`mcp-server`) instead lives in `docker-compose.dev.yml`, an override file layered on top.

`Makefile`'s `ENVIRONMENT` (`.env`, default `development`) picks which files `check-env` puts in `COMPOSE_FILES`: anything but exactly `production` layers both files (today's dev workflow, unchanged); `production` uses `docker-compose.yml` alone. Every target depends on `check-env`, which prints `⚠️  ENVIRONMENT=...` before anything else runs. `ENVIRONMENT` is captured from the shell/`.env` *before* `include .env` runs and restored after, specifically so a shell-exported `ENVIRONMENT=production make start` isn't silently overwritten by `.env`'s own `ENVIRONMENT=development` default (`include`'s plain `=` assignment is file-origin, which GNU Make lets override an environment-origin variable - the reverse of what you'd expect).

Static per-image config (Grafana provisioning, LiteLLM's `config.yaml`, `redis.conf`, etc.) is still baked into each service's own image via `COPY` in its Dockerfile, in both dev and prod - that part of the "bake config, don't bind-mount it" convention (`clickhouse`/`prometheus`/`loki`/`blackbox`) is unchanged. What moved is *runtime role selection* for the one image that serves four different compose services (`webhook`/`webhook-worker`/`webhook-reparse`/`clickhouse-migrate`, all built from `services/webhook/Dockerfile`): instead of a compose-level `command:` picking the entry point, `services/webhook/docker-entrypoint.sh` (baked, `ENTRYPOINT`) dispatches on the `APP_ROLE` env var (`server`/`worker`/`reparse`/`migrate`, default `server`) set per-service in `docker-compose.yml`'s `environment:`. It also has an `if [ "$#" -gt 0 ]; then exec "$@"; fi` passthrough, so `docker-compose.dev.yml`'s `command:` override (adding `--reload` for `webhook`) still works without touching the script. `litellm` and `redis` get **no** dev override at all - both environments always run the same baked image (editing `services/litellm/config.yaml`/`services/redis/redis.conf` needs a rebuild in dev too, same as `clickhouse` already works).

## ClickHouse schema migrations (`services/clickhouse/migrations/`)

`mcp-server`'s `query` tool is read-only by validation (SELECT/WITH only,
DDL keywords rejected server-side - see "Rules to not violate" below), so no
agent can run a schema change through it. Any change to `agent_events`,
`agent_usage`, `agent_messages`, or `ingest_raw` (new column, engine
change, new table) happens in the main conversation with Bash, the same way
`services/clickhouse/migrations/001_replacing_mergetree.sql` was applied:

- One `.sql` file per migration in `services/clickhouse/migrations/`,
  numbered in order (`002_...`, `003_...`, ...) with a short, descriptive
  name.
- Start the file with a comment block explaining *why* the migration is
  needed (what's broken/missing without it), not just what it does.
- Write every migration so a second run is a no-op: `CREATE TABLE IF NOT
  EXISTS`, guard `ALTER TABLE ... ADD COLUMN IF NOT EXISTS`, check current
  state before a rename/swap rather than assuming a clean starting point.
- If the migration includes a BACKFILL (populating a new/changed column
  from existing data), make the backfill itself idempotent/run-once too -
  e.g. gate it on the column still being at its default, or use `INSERT ...
  SELECT` into a dedup-by-engine target rather than an unconditional
  `UPDATE`-style rewrite. Re-running the file must not double-apply the
  backfill.
- Test the migration's queries (the `SELECT` parts, and any query that will
  read the changed schema afterward) via the ClickHouse MCP tool before
  considering the migration done, same as any other query - see
  `clickhouse-analyst`.
- docker-entrypoint-initdb.d only applies `services/clickhouse/schema.sql`
  to a brand-new empty volume, so also update `schema.sql` to match the new
  end state - migrations are for existing stacks, `schema.sql` is what a
  fresh stack gets.

## cAdvisor container-level metrics (`observability` profile)

`cadvisor` resolves a container's name/image/rw-layer via the classic `overlay2` graphdriver `layerdb` layout. Any Docker install using the containerd-snapshotter storage driver instead (current Docker Desktop by default; also selectable under Colima) breaks this outright - `failed to identify the read-write layer ID`, and the dashboard's `$container` variable (`label_values(container_last_seen{name!=""}, name)`) comes back empty since no container ever gets a `name` label. Mounting `docker.sock` or pointing `--containerd` at the daemon's own containerd socket does not work around it - cAdvisor's cgroup-path-based docker detection takes over regardless. The only fixes are disabling containerd-snapshotter for that install, or a plain Linux Docker host (classic overlay2), as in production. `cadvisor` stays in the `observability` profile regardless of this, since `node_exporter`-backed host-wide metrics (the dashboard's "Host" tab) aren't affected and still work.

## Backup & restore (`services/backup/`)

Backs up/restores the three services with state not reproducible from the
repo (`clickhouse`, `litellm-db`, `grafana`'s `grafana.db`) via the `backup`
tools-profile service. Full playbook (setup, `make backup-*`/`restore-*`
usage, per-service restore steps, cron) lives in README.md's "Backup &
restore" section - read that when you actually need the mechanics, don't
duplicate it here. Rules to not violate either way:

- **Backup is always safe to run against a live stack; restore is always
  destructive** - it drops/overwrites the live target, and for
  `litellm`/`grafana` specifically requires that service stopped first
  (the `backup` container never gets Docker API/socket access, so it can't
  stop/start sibling containers itself).
- **Cron only ever calls `make backup-all`.** Never point a cron job at a
  `restore-*` target - restore stays a manual, deliberate action taken by a
  human who's read README.md first.
- **No automatic pruning/retention** - `.backups/` (or `$BACKUP_DIR` if set)
  accumulates every backup file until removed by hand. Don't add a
  retention/cleanup step without being asked; it was deliberately left out.

## Running tests

`make test` runs `services/webhook/tests` - a pytest suite for every function in `services/webhook/src/clickhouse_ingest.py` that doesn't touch ClickHouse (row/id/text parsing, not the `client.insert`/`client.query` calls). It needs no live ClickHouse or docker-compose stack: `services/webhook/tests/conftest.py` stubs the required `CLICKHOUSE_*` env vars before import, and every test loads a real captured payload from `services/webhook/tests/captures/*.json` (copies of actual `services/webhook/captures/<session_id>/*.json` files) rather than hand-built fixtures.

First-time setup: `.venv/bin/pip install -r services/webhook/requirements-dev.txt` (installs `services/webhook/requirements.txt` plus `pytest`).

Always run tests through the `webhook-test-runner` agent (`.claude/agents/webhook-test-runner.md`, runs on Haiku) rather than calling `make test`/`pytest` directly - see the rule below. It reports back a per-test PASSED/FAILED listing plus a summary line, without spending main-conversation context on raw pytest output.

## Running the load test (`make loadtest`)

Whenever the user asks for a load test, delegate the whole workflow to the `loadtest-runner` agent (`.claude/agents/loadtest-runner.md`, runs on Sonnet) rather than driving `make loadtest` inline - it owns the ask-first questions below, launching, parallel monitoring, ClickHouse verification, and the final bottleneck report end to end.

Before starting a `make loadtest` run, **ask the user** (don't assume) about three things:

- **Whether to truncate the ClickHouse ingest/agent tables first** (`agent_events`, `agent_invocations`, `agent_messages`, `agent_usage`, `ai_gateway_groups`, `ai_gateway_users`, `ingest_dlq`, `ingest_raw`, `plan_proposals`, `session_git_branch` - never `schema_migrations`). A clean baseline makes before/after row counts meaningful, but isn't always wanted.
- **Whether to restart the whole stack first** (`docker compose down` + back up, or equivalent) so every service starts from a known-good, non-degraded state before the run, rather than reusing whatever state containers happen to be in.
- **Whether to shut down `litellm`/`litellm-db` first, if they're currently up** - they share the same Docker host/resources as everything the load test measures, and load tests don't use them anyway (`loadtest.py` hits `webhook`/`load-balancer` directly, bypassing LiteLLM), so leaving them running is a free variable in the resource measurements unless the user wants them left alone for something else.

After the run, **ask before leaving `litellm`/`litellm-db` up** if they were shut down for the test (bring them back?) or if they were only started to verify something unrelated (e.g. a backup) beforehand - don't just assume either way.

If the stack gets stopped/restarted (accidentally or otherwise) while a load test or its monitoring loop is still running, treat the in-flight run as contaminated - stop the loadtest container and any monitoring process, don't try to salvage partial data, and re-run from a clean start once the stack is confirmed healthy again.

## Comment policy

- **Comment code/config economically.** Code is read rarely and comments rot faster than the code they describe. A comment should cover a non-obvious *why* (a hidden constraint, a workaround, an invariant that would surprise a reader) - not restate what the code already says. Don't try to fully document behavior in a comment; that's what clear naming/structure and tests are for. If you're about to write more than a short paragraph inline, that's a sign the content belongs in `AGENTS.md` (for future agents) or `README.md` (for users) instead, with just a pointer left in the comment.
- **Comments describe the general/hypothetical case, never this specific machine's state.** Write "this breaks under Docker Desktop's containerd image store" or "this breaks under Colima when the containerd-snapshotter driver is enabled," not "this is broken on this machine" or "confirmed broken in this dev environment." A fact about one person's current setup belongs in that person's own notes, not in a comment every future reader (on a different machine, in production) will trip over. The one exception is memory (`~/.claude/projects/*/memory/`, outside this repo) - that's explicitly the right place for machine-specific/session-specific state.
- **The main architectural picture lives in `AGENTS.md` (for agents) and `README.md` (for users) - not scattered across inline comments.** After any change that alters architecture (a new service, a changed data flow, a new required env var, a new failure mode worth knowing about), check whether `.env.example`, `README.md`, and `AGENTS.md` need updating, and update them. This step is easy to skip and easy to forget - treat it as part of the change, not a follow-up.

## Rules to not violate

- **Run the test suite after every change under `services/webhook/` (source or tests) - always via the `webhook-test-runner` agent, never `make test`/`pytest` inline.** Delegating keeps raw pytest output (35+ lines and growing) out of the main conversation, per this repo's usual pattern of pushing DB reads/tool output into subagents (see `clickhouse-analyst`). Do this proactively, without being asked - don't wait for the user to request a test run.
- **Skills, agents, and any config/naming this repo owns must stay CLI-agnostic.** This stack tracks Claude Code and Codex CLI equally - don't write a skill/agent body that only makes sense for one of them without saying so explicitly, and don't name a variable/file after "Claude" when the thing it controls is actually shared (a now-retired hook-era variable, `CLAUDE_TRACKING_API_URL`, once did exactly this - see git history if precedent is needed). The one exception: names Claude Code or Codex itself defines (`CLAUDE_PROJECT_DIR`, `.claude/`, `.codex/`) - don't rename those, they aren't ours to rename.
- **No per-service env defaults in Python/entrypoint code.** `docker-compose.yml` is the only place `CLICKHOUSE_*`/`REDIS_*` defaults live; `services/webhook/src/config.py` reads them with plain `os.environ[...]` (no fallback), and `services/grafana/docker-entrypoint.sh` asserts (`:?`) rather than re-defaulting. A second copy of the defaults has drifted before (the old ingest-api once silently defaulted the password to `""`).
- **Every tunable constant in `webhook`/`webhook-worker` lives in `services/webhook/src/config.py`, not scattered across modules.** `clickhouse_ingest.py`, `queue_client.py`, `worker.py`, and `server.py` all import from `.config` rather than reading `os.environ` or hardcoding their own constants - a new tunable (queue mechanics, connection settings, feature flags like `CAPTURE_ENABLED`) belongs there too, even if only one module currently uses it.
- **Never derive cost from a local price table again.** `agent_usage.cost`/`input_cost`/`output_cost` come straight from LiteLLM's own `response_cost`/`cost_breakdown` - a manually-maintained `model_pricing` table with an `ASOF JOIN` derivation used to exist for this and was removed after it was found to overcount cost by several times whenever prompt caching was in play (it priced every input token at full rate, ignoring the cache-read/cache-write discount LiteLLM already applies correctly).
- **`schema.sql` changes need a manual re-apply** on an already-initialized volume: `docker exec -i agent-tracking-clickhouse clickhouse-client --multiquery < clickhouse/schema.sql`, or drop the `clickhouse-data` volume (destroys data).
- **Bump the version whenever you edit an agent's, skill's, or command's behavior - but never by touching the invocation identifier.** Claude Code has no notion of a `version:` frontmatter field (it only ever reads `name:`/`description:`, and for a command only the file's own body), so a version is only ever visible in the LiteLLM-logged conversation if it rides along inside one of those. Renaming the identifier itself used to be how this worked (`<name>_v<version>` baked into a Subagent's `name:` or a Skill's directory name) and was abandoned: a Skill's directory name is its actual invocation identifier, so bumping the version meant renaming the directory, which could break an in-flight session still referencing the old name. Instead:
  - **Subagent** (`.claude/agents/*.md`): `name:` stays bare, permanently. Put `<agent_version>X.Y.Z</agent_version>` as the very first thing in `description:` - that text is injected verbatim into every call's `messages` via the "Available agent types" system-reminder listing (confirmed against a real captured payload; the agent's own body/system-prompt is *not* logged), so the marker rides along without needing the identifier to change. Recovered by `clickhouse_ingest.py`'s `_agent_invocations_from_messages`/`_version_marker_for_name`.
  - **Skill** (`.claude/skills/<dirname>/SKILL.md`): directory name stays bare, permanently - never rename it again. Same `<skill_version>X.Y.Z</skill_version>` marker as the first thing in `description:`, surfaced the same way via the "available skills" listing. Recovered by `_skill_name_and_version`.
  - **Command** (`.claude/commands/*.md`): filename stays bare, permanently. There's no persistent "available commands" listing, so the marker instead goes in the command file's own body (after the frontmatter) as `<command_version>X.Y.Z</command_version>` - that body text is what gets expanded into the triggering message alongside the `<command-name>` tag Claude Code already injects. Recovered by `_active_command_name_and_version`.
  - A self-named/ad-hoc agent (`general-purpose`, `Explore`, `Plan`, ...) has no backing file and no marker - version comes back blank, same as an entry never edited since creation.
- **When creating a brand-new Subagent/Skill/Command, don't add a version marker at all** - start unmarked, not `<agent_version>1.0.0</agent_version>`. Only add the marker once it has actually shipped and you're editing its behavior later, per the rule above.
- **When bumping an existing version marker, ask the user which semver segment to bump - patch, minor, or major - showing the resulting `X.Y.Z` for each option** (e.g. via `AskUserQuestion`), rather than deciding unilaterally. Don't ask again mid-conversation once they've told you their intent for the current edit (e.g. "this is a bugfix, patch it" up front) - only ask when it's genuinely ambiguous which kind of change this is.
- **`webhook`/`webhook-worker` stay write-only for external/interactive reads.** All human/agent investigation goes through `mcp-server`, never `docker exec`-ing into ClickHouse directly. The one exception is internal to `clickhouse_ingest.py` itself: resolving `agent_invocation_id` → `subagent_type` needs a `SELECT` against `agent_invocations` before the write it's completing - that's part of the ingestion path, not a general read API, so it doesn't count against this rule.
- **`build_event()`'s `source_row` carries the full, untouched payload (`messages` included) - that's deliberate, not a leak.** It's the one field that isn't stripped down, since `ingest_raw` (see `clickhouse/schema.sql`) exists precisely to hold the full payload for later reparsing (`webhook/src/reparse.py`) - Redis is just the buffer in front of that ClickHouse write, same as it is for the compact per-table rows. `config.MAXLEN`/the `redis` service's `maxmemory` are sized around this larger (~360KB avg, ~1.5MB max) per-event footprint (see `services/webhook/config.yml`) - don't add a new field to `build_event()`'s dict without checking it against that budget.
- **`clickhouse-analyst`'s tools stay limited to `mcp__clickhouse__query`/`whatsup`.** Never add it Bash or any other direct ClickHouse access - all reads must go through `mcp-server`, per the rule above.
- **Any read of `services/grafana/dashboards/agents_overview.json` - listing panels, finding one by id/title, dumping a query, checking current `queryOptions`/`fieldConfig`/etc. - goes through the `dashboard-parser` agent, never inline `python3`/`jq`/`Read` in the main conversation.** This includes quick one-off checks and post-edit verification, not just the initial investigation - the file is large (v2beta1 schema) and re-reading it inline defeats the point of delegating. Writes (the actual JSON edit) still happen in the main conversation via `Edit`/`Write`/Bash-python, since `dashboard-parser` has no write tools - only the reading step is delegated.
- **`dynamictext-panel-builder` is scoped to Dynamic Text panels only (panel-76 "Trace" and its companion panel-77), not the whole dashboard.** Every other panel edit in `agents_overview.json` goes through `dashboard-panels-builder` instead (which reads the `dashboard-panels` skill before editing) - `spec.annotations`, `spec.variables`, dashboard-level settings, and tabs/layout stay plain `Edit`/`Write`/Bash-python in the main conversation, since neither panel-builder agent owns those.
- **`file-ops`/`script-ops` never get `git` (and `file-ops` never gets `Bash`).** Blast-radius judgment calls (`git`, and any state-changing `docker` command - `up`/`down`/`restart`/`build`) stay with the caller, not a delegate. **Read-only `docker`/`docker compose` inspection (`ps`, `logs`, `inspect`) always goes through `script-ops`, never inline `Bash` in the main conversation** - `docker logs` output especially is exactly the large, mechanical dump `script-ops` exists to keep out of the main conversation's context; for anything with potentially large output, it should redirect to a file and `grep` it rather than dumping the full output back.
- **Never restart/recreate `clickhouse` or edit an existing Grafana dashboard (`agents_overview.json`) as a side effect of unrelated infra work.** Both are higher blast-radius than adding a new standalone service - treat them as a separate, explicitly-requested final step, done and confirmed on their own.
- **When validating a dashboard panel's SQL fix against ClickHouse, test the panel's literal `rawSql` with only `${...}` placeholders substituted - never a simplified/reconstructed rewrite.** A trimmed test query that drops a join/column that looks like template-variable plumbing can pass cleanly while the real query still fails (e.g. `AMBIGUOUS_IDENTIFIER` from a dropped join that was actually load-bearing).
- **Don't loosen `_validate_readonly_sql` in `services/mcp-server/src/server.py`.** There's no separate read-only ClickHouse user backing `query` - that function (single statement, SELECT/WITH only, no DDL/DML keywords, no system tables, no remote/file/URL table functions) is the only thing standing between it and a write/DDL statement.
- **No per-service `README.md` files under `services/*/`.** A full playbook for a service (setup, operation, restore procedures, etc.) belongs in the repo-root `README.md`, not a separate `services/<name>/README.md` - `services/backup/README.md` used to duplicate what's now README.md's "Backup & restore" section and was folded in and deleted for exactly this reason. `AGENTS.md` (this file) stays the terse, agent-facing summary with just the essentials and rules; `README.md` is the one place for the full, detailed mechanics a human (or an agent that rarely needs the details) would read. Don't reintroduce a per-service README even for a new service.
- **Never restart/recreate the `litellm` container without asking first, even for a config-only change (`services/litellm/config.yaml`, `custom_callbacks.py`, `docker-entrypoint.sh`).** It's the live proxy every CLI session on the machine routes through - a restart drops in-flight requests for whoever else is using it right now. Ask before `docker compose restart litellm` / `docker compose up -d litellm`, the same way you would before any other action that affects shared, currently-in-use infrastructure. Note the two aren't interchangeable once asked: `restart` reuses the container's existing environment snapshot and won't pick up new/changed `environment:` entries in `docker-compose.yml` - only `up -d` (recreate) does. Confirmed the hard way: `LANGFUSE_PUBLIC_KEY`/`SECRET_KEY` were added to `litellm`'s `environment:`, then `litellm` was `restart`ed instead of recreated - it ran for a while looking fine with zero Langfuse traces produced, because the running container never actually had the new vars.
- **Never run `docker compose build`/`docker compose up` directly - always `make build [SERVICE=<name>]`/`make up [SERVICE=<name>]` instead** (both accept an optional `SERVICE` to scope to one service; omit it to cover the whole stack). `Makefile` resolves each image group's tag from `VERSIONS.yml` via `scripts/resolve_image_version.py` into `.image-tags.mk`, which exports the `<SERVICE>_TAG` vars `docker-compose.yml`'s `image: ...:${..._TAG:-latest}` lines depend on - a raw `docker compose build`/`up` skips that resolution and produces stray image versions untied to `VERSIONS.yml`.

## Git: ask before destructive actions

**Never run `git checkout --`/`restore`/`reset --hard`/`clean` (or any other command that discards uncommitted working-tree changes) without asking first - even to undo your own bad edit, and even on a file that looks like it only contains your own changes.** `git status` at the start of a session can't tell you whose changes are sitting there uncommitted or how far back they go; a file already showing as modified before you touched it is signal that discarding it isn't yours to decide. Recovery is normally not possible - `git checkout` on a path that was never `git add`ed leaves no blob to recover from `git fsck`/reflog, and IDE-level local history requires the IDE to have actually been running.

Concretely: if a change you just made needs undoing, edit it back by hand (or re-apply a narrower fix) instead of reaching for a git command that reverts the whole file to `HEAD` - that also wipes out any pre-existing uncommitted work in the same file, not just your own last edit. This happened for real: a `docker compose` v2beta1 dashboard edit came out reformatted (`json.dump` rewrote the whole file's whitespace), the fix was `git checkout -- <file>` to "undo just that," and it silently discarded unrelated uncommitted dashboard work that had been sitting in the same file since before the session started - work that turned out to be recoverable only because another session happened to still have it.

**This rule binds every delegated subagent too, not just the main conversation - having Bash/git access doesn't make a subagent exempt.** It happened a second time for real: mid-task on `agents_overview.json`, `dynamictext-panel-builder` compared the live file against stale `HEAD` instead of the actual working tree, misdiagnosed a large pre-existing uncommitted diff as its own corruption, and ran `git checkout -- <file>` to "recover" - wiping a full session's worth of uncommitted dashboard work. It only survived because an IDE's local-history autosave happened to flush a buffer back over the checkout moments later - luck, not a safety net. Any agent definition (`.claude/agents/*.md`) granted `Bash` on a file known to carry uncommitted work must be told explicitly: if the file's state looks wrong mid-task, stop and report the anomaly back to the caller instead of self-recovering with git - diagnose by reading/grepping the file's actual current content, never by diffing against a git baseline that's likely stale relative to real uncommitted work already sitting there.
